# Сервис рекомендаций товаров (Retailrocket)

Сервис по `visitorid` возвращает top-k товаров для блока рекомендаций на главной странице магазина.

## 1. Постановка задачи и метрики

- **Бизнес-цель:** рост продаж (оборота). На главной три слота с рекомендациями, значит нужны три товара, которые пользователь с наибольшей вероятностью добавит в корзину или купит.
- **Техническая метрика: Precision@3** — доля релевантных товаров среди трёх показанных, усреднённая по пользователям.
  - Релевантный товар: пользователь сделал `addtocart` или `transaction` по нему в тестовом периоде.
  - Усредняем по **всем** 8 343 пользователям, у которых в test есть корзина или покупка. Если их покупки не попали в пул кандидатов, пользователь учитывается с нулём. Отбрасывать таких пользователей нельзя, иначе метрика завышается.
- **Связь с бизнес-метрикой:** Precision@3 — оффлайн-прокси для CTR/конверсии блока. Оборот можно оценить только A/B-тестом, оффлайн его не посчитать.

## 2. Данные

Датасет Retailrocket (интернет-магазин), 4 файла:

| Файл | Колонки | Тип данных |
|---|---|---|
| `events.csv` (2,76 млн строк) | timestamp (unix, мс), visitorid, event (`view`/`addtocart`/`transaction`), itemid, transactionid | лог поведения, неявная обратная связь |
| `category_tree.csv` | categoryid, parentid | дерево категорий |
| `item_properties_part1/2.csv` (~20 млн строк) | timestamp, itemid, property, value | история свойств товара. Свойства захешированы, кроме `categoryid` и `available`. Используем `categoryid`, `available` и `790` (числовое, по распределению похоже на цену, это гипотеза) |

Анализ данных и генерация факторов: `feature_generation.ipynb`. Выводы: данные сильно разрежены, у товаров «длинный хвост», корзины и покупки составляют около 3 % событий, большинство пользователей приходит один раз.

## 3. Факторы (38 штук, `app/features.py`)

- **Товар (20):** просмотры/корзины/покупки, число пользователей, конверсии (`cart_rate`, `buy_rate`, `buy_per_cart`), активность за последние 1 и 7 суток и доля недели, перцентильные ранги популярности и покупок, давность последнего события, возраст, наличие, лог-цена и цена относительно категории, конверсия и глубина категории, `categoryid`.
- **Пользователь (10):** число событий по типам, число товаров и сессий (пауза > 30 мин), давность последнего события, конверсии в корзину и покупку, средняя цена.
- **Пара пользователь–товар (8):** просмотры/корзины/покупки пары, часов с последнего события, тип последнего события, признак «товар из истории», события пользователя в категории товара и их доля.

Полный список (имена колонок как в `FEATURES`):

| Группа | Признаки |
|---|---|
| Товар (20) | `item_views`, `item_carts`, `item_buys`, `item_users`, `item_cart_rate`, `item_buy_rate`, `item_buy_per_cart`, `item_events_last1d`, `item_events_last7d`, `item_trend_7d`, `item_pop_rank`, `item_buy_rank`, `item_days_since_last`, `item_age_days`, `item_available`, `item_log_price`, `item_price_vs_cat`, `cat_buy_rate`, `cat_depth`, `categoryid` |
| Пользователь (10) | `user_views`, `user_carts`, `user_buys`, `user_events`, `user_items`, `user_sessions`, `user_days_since_last`, `user_cart_rate`, `user_buy_rate`, `user_mean_price` |
| Пара (8) | `ui_views`, `ui_carts`, `ui_buys`, `ui_hours_since_last`, `ui_last_event` (0 — view, 1 — addtocart, 2 — transaction, −1 — нет истории), `ui_in_history`, `ui_cat_events`, `ui_cat_share` |

Все признаки считаются **только по train**. Свойства товаров берутся «на момент отсечки», будущее не используется.

## 4. Формат входных данных для обучения, преобразование датасета и валидация

**Входные данные для обучения** — таблица пар «пользователь–товар» (одна строка = одна пара-кандидат), которую строит `train.py` из `events.csv` и `features/*.pkl`:

| Колонка | Тип | Описание |
|---|---|---|
| `visitorid` | int | пользователь, служебная колонка (группа для `GroupKFold`, не признак) |
| `itemid` | int | товар, служебная колонка (не признак) |
| 38 признаков | float32 | факторы из раздела 3: 20 по товару, 10 по пользователю, 8 по паре |
| `target` | int8 | 1, если в test пара получила `addtocart` или `transaction`, иначе 0 |

Список и порядок признаков зафиксирован в `app/features.py` (`FEATURES`) и сохраняется в `artifacts/meta.json`. Одним и тем же кодом признаки строятся и при обучении, и в сервисе. Счётчики пары без истории заполняются нулём, тип последнего события — `-1`, остальные пропуски остаются `NaN`, XGBoost обрабатывает их сам.

**Трансформации исходного датасета:**

1. Время делим по квантилю 0,8 (`cutoff` = 2015-08-18 04:23 UTC, `features/meta.pkl`): первые 80 % событий — train, остальные 20 % — test. Случайный split дал бы утечку будущего.
2. **Кандидаты** для пользователя: товары из его истории в train и пул популярных товаров (40 лучших по корзинам+покупкам и 40 лучших по активности за последние 7 суток, всего 69 товаров).
3. **Цель** `target` = 1, если пара (пользователь, товар) в test имеет `addtocart` или `transaction`.
4. Обучающая выборка: все 8 343 пользователя с положительной меткой в test и 5 000 случайных остальных. Получилось 947 836 пар, из них 976 положительных.
5. **Валидация:** 5-fold `GroupKFold` по пользователю (один пользователь не попадает одновременно в train и valid). Precision@3 считается по out-of-fold-предсказаниям.

> Исходная цель из `feature_generation.ipynb` (только пары из истории train) даёт всего 365 положительных пар на 1,7 млн. У 89 % пользователей с покупками в test истории в train нет вообще, поэтому в кандидаты добавлен пул популярных товаров.

## 5. Эксперименты

Precision@3, 5-fold CV по пользователям, 8 343 пользователя. Максимум при таком пуле кандидатов: 976 / 3 / 8343 ≈ 0,039.

| Модель | Гиперпараметры | P@3 | P@3, пользователи с историей (896) | P@3, холодные (7 447) |
|---|---|---|---|---|
| Популярное: корзины+покупки | — | 0,00515 | | |
| Популярное: активность за 7 дней | — | 0,00348 | | |
| Недавняя история пользователя | — | 0,00779 | | |
| XGBoost classifier, **выбрана** | depth 3, 200 деревьев, lr 0,05 | **0,01478** | 0,0759 | 0,0074 |
| XGBoost classifier | depth 5, 200 деревьев, lr 0,05 | 0,01478 | 0,0759 | 0,0074 |
| XGBoost classifier | depth 5, 200, lr 0,05, scale_pos_weight 31 | 0,01426 | 0,0711 | 0,0074 |
| XGBoost classifier | depth 7, 400, lr 0,03, scale_pos_weight 31 | 0,01354 | 0,0644 | 0,0074 |
| XGBoost ranker (rank:pairwise) | depth 5, 200, lr 0,05 | 0,01442 | 0,0725 | 0,0074 |

Общие параметры: `subsample=0.8`, `colsample_bytree=0.8`, `tree_method=hist`. Полные результаты лежат в `docs/experiments.json`.

**Итог:** XGBoost даёт P@3 = **0,0148**, это в 1,9 раза выше лучшего бейзлайна (недавняя история, 0,0078) и в 2,9 раза выше «просто популярного» (0,0052). У пользователей с историей P@3 = 0,076. Самые важные признаки: `ui_carts`, `ui_cat_share`, `ui_hours_since_last`, `item_available`, `item_buy_rank`.

Ограничения:
- Абсолютные значения низкие: целевое событие редкое, а 89 % покупателей в test новые. Для них (холодный старт) модель ранжирует только по признакам товара, поэтому разные конфигурации дают на них одинаковый результат.
- Не реализованы коллаборативная фильтрация и факторизационные машины, заявленные в плане. Это следующий шаг, он должен помочь именно холодным и редким пользователям.

## 6. Устройство сервиса

```
service/
  app/main.py         FastAPI: эндпоинты, валидация, метрики Prometheus
  app/recommender.py  кандидаты -> признаки -> XGBoost -> top-k
  app/features.py     сборка признаков (общий код с обучением)
  artifacts/          model.json + таблицы признаков (items, users, ui, ucat) + meta.json
  train.py            обучение и оценка, пишет artifacts/ и docs/experiments.json
  tests/test_api.py   тесты API
  Dockerfile, requirements.txt
```

На запросе берётся история пользователя и пул популярных товаров, строятся признаки пары, XGBoost их оценивает и возвращает top-k. Неизвестный пользователь получает ранжированный пул популярных товаров (`strategy: popular_fallback`). Некорректные запросы дают `422`, сервис остаётся рабочим. Время ответа около 0,1 с (замер `curl` на сервере для `/recommend/8`).

## 7. API

| Метод | Путь | Описание |
|---|---|---|
| GET | `/recommend/{user_id}?k=3` | рекомендации, `k` от 1 до 10 (по умолчанию 3) |
| POST | `/recommend` | то же, тело `{"user_id": 8, "k": 3}` |
| GET | `/health` | статус, модель и значение метрики |
| GET | `/metrics` | метрики Prometheus (список в разделе 9): запросы по стратегиям, задержка, скор, HTTP-статусы, качество модели |
| GET | `/docs` | интерактивная документация Swagger |

Пример:

```bash
curl http://localhost:8000/recommend/8
```
```json
{"user_id": 8, "strategy": "personalized",
 "recommendations": [{"rank": 1, "item_id": 461686, "score": 0.00039},
                     {"rank": 2, "item_id": 320130, "score": 0.00016},
                     {"rank": 3, "item_id": 384302, "score": 0.00016}]}
```

POST с телом JSON:

```bash
curl -X POST http://localhost:8000/recommend -H "Content-Type: application/json" -d '{"user_id": 8, "k": 2}'
```

Поля ответа: `user_id`; `strategy` (`personalized` — пользователь есть в истории, `popular_fallback` — холодный старт, выдаются популярные товары); `recommendations` — список из `k` элементов `{rank, item_id, score}`, где `score` — вероятность корзины или покупки по модели.

Ошибки: `user_id` не число, отрицательный или `k` вне 1..10 дают `422` с описанием поля, сервис продолжает работать:

```bash
curl -i http://localhost:8000/recommend/abc          # 422, input should be a valid integer
curl -i "http://localhost:8000/recommend/8?k=50"    # 422, input should be less than or equal to 10
```

Метрики для Prometheus: `curl http://localhost:8000/metrics`.

## 8. Запуск

Docker (из папки `service/`):

```bash
docker build -t recsys:1.0 .
docker run -d --name recsys -p 8000:8000 recsys:1.0
curl http://localhost:8000/health
```

Запуск из переданного файла `recsys-1.0.tar` (на машине достаточно одного Docker, исходники не нужны):

```bash
docker load -i recsys-1.0.tar
docker run -d --name recsys -p 8000:8000 recsys:1.0
curl http://localhost:8000/health
```

Сервис готов через 10–60 секунд после старта (загружает модель и таблицы признаков), контейнер сообщает статус `healthy`. Образ самодостаточный: модель и таблицы признаков лежат внутри. Остановка: `docker rm -f recsys`.

Экспорт образа в файл (так получен `recsys-1.0.tar`):

```bash
docker save -o recsys-1.0.tar recsys:1.0
```

Без Docker:

```bash
pip install -r requirements-dev.txt
python -m uvicorn app.main:app --port 8000
python -m pytest tests
```

Переобучение (из корня проекта, нужны `events.csv` и `features/`):

```bash
python service/train.py
```

## 9. Мониторинг: Prometheus и Grafana

```bash
docker compose up -d --build
```

| Сервис | Адрес | Назначение |
|---|---|---|
| recsys | :8000 | сервис, метрики на `/metrics` |
| Prometheus | :9090 | забирает метрики каждые 15 с |
| Grafana | :3000 | дашборд «Recsys: метрики сервиса и модели» (логин `admin`, пароль из `GRAFANA_PASSWORD`, по умолчанию `admin`) |

В `docker-compose.yml` папка `artifacts/` смонтирована в контейнер, поэтому после `python service/train.py` модель обновляется командой `docker compose restart recsys`, без пересборки образа.

Метрики: `recsys_requests_total{strategy}`, `recsys_request_seconds` (задержка), `recsys_top_score` (скор лучшего товара, индикатор дрейфа), `recsys_http_requests_total{path,status}`, `recsys_model_precision_at_3_cv`, `recsys_model_info`. Источник данных и дашборд подключаются автоматически (provisioning).
